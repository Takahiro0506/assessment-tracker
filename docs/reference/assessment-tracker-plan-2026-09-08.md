# アセスメント管理Webアプリ：操作試作の方針

整理日：2026-09-08

## 目的

AIを使って開発し、自分の商品から少額でも利益を得る経験をする。アプリ内AI・AI API・PDF取り込みは使わない。ポートフォリオ制作を主目的には置き換えない。

## 今回進める範囲

複数科目の課題を簡単に登録でき、未提出・結果待ち・再提出を把握できる操作試作。収益性が確認済みとは扱わない。まずローカルで使える形にする。

## 操作

- 一覧へ科目名、課題名、締切を直接入力する。締切未定も保存できる。
- 科目名は入力中に新規作成でき、既存の名前を選び直せる。科目の事前登録は必須にしない。
- 複数行を続けて入力できる。仮名課題の一括作成は初期必須にしない。
- 課題の状態は「作業が必要」「提出済み・結果待ち」「完了」。初回か再提出かは別に示す。
- 提出済みにすると作業対象と区別される。再提出期限を追加すると作業対象へ戻る。
- 再提出時には過去の期限・提出記録を維持する。
- 名前・締切を訂正できる。完了した課題は通常の作業一覧から片付ける。
- 削除対象と履歴も削除されることを明示する。削除と完了は別操作にする。

## 画面

中心は一画面。締切順の作業一覧を基本とし、期限未定を埋もれさせない。結果待ち・完了も同じ画面から確認できる。PCは連続入力、スマホは確認と更新を重視する。表示言語の初期案は英語。対象利用者に合わせた表示文言は試作で確認する。

## 試作の保存

ブラウザ内保存を初期案とする。再読み込みしても状態を保持するが、端末間同期はない。ブラウザデータの削除で消える可能性を明示する。試験データの書き出し・復元を用意し、架空データと本人入力を区別する。

## 初期試作から外すもの

AI、PDF、学校システム連携、自動学習計画、所要時間、優先度、「今日やる」、外部通知、認証、クラウド同期、決済、学校の評価規定・試行上限の自動判定。

認証・同期・決済は、操作試作を評価した後の商品版で必要性と費用を決める。個人用記録であり学校の公式結果を示すものではない。

## 比較する場面

1. 平常時：少数の課題を登録・確認する。
2. 集中時：複数科目に締切未定・未提出・結果待ち・再提出が混在する。

件数は検証シナリオであり市場の事実ではない。本人が苦労した週の状況を再現できる場合は、それを優先する。

比較対象は利用者が今使っている方法。初回登録にかかった時間、登録ミス、未提出・結果待ちを正しく見つけられるか、迷った箇所を記録する。更新時間も測れるが、数秒差だけを購入理由とはしない。

開発者の自己テストは動作確認として行う。使いやすさの評価は初見の対象利用者にも依頼し、両者を分けて記録する。誘導の有無や操作順にも注意する。少人数の結果から市場規模は推定しない。

## 課金・集客

試用期間、価格、利用期限は未決定。14日・45日・A$9.90・180日は過去の仮案であり、採用済みの仕様ではない。実際に役立つ場面と継続利用を確認してから販売条件を決める。

対象学生への到達経路は未確保。職務上の学生を当然の販売先にはしない。購入意思と実際の購入は区別する。

## 開発・公開方針

ローカル開発から始める。アプリのソースは同期参照資料と分離した専用ディレクトリ・Gitリポジトリで管理する。既存のsources/は編集しない。

GitHub CLIはTakahiro0506で認証済み（整理時点）。現在のプロジェクトルームのディレクトリ自体はGitリポジトリではない。アプリのリポジトリ作成・push・公開はまだ実施していない。

公開先はCloudflare Pagesの無料枠を第一候補とし、接続・利用条件は公開時に確認する。Vercel Hobbyは非商用の個人利用向けという制限があるため、収益化前提で既定の公開先にはしない。初期試作はサーバー・独自ドメイン購入なしで動かせる構成を選ぶ。

出典：[Vercel Hobby](https://vercel.com/docs/plans/hobby)、[Cloudflare Pages料金](https://developers.cloudflare.com/pages/functions/pricing/)

## 試作後の判断

登録・状況把握の負担が既存手段より減るか、実際の学生が自発的に再利用するかを確認する。改善が見えれば商品版を検討する。差が出なければ機能を追加して延命せず、原因を記録して設計変更または見送りを判断する。
