# バックアップと復元

更新：2026-09-11。クラウド同期はバックアップではない。復元手段と保管場所を分ける。

| 手段 | 保存場所・保持 | 戻せるもの | 限界 |
|---|---|---|---|
| 下書き・未同期コピー | 同じブラウザ、同じアカウントのキー | 送信前・通信失敗時の作業 | ブラウザ消去・端末喪失では失われる |
| ごみ箱 | D1の現在データ、期限なし | 誤って移動したカードと履歴 | DB自体の喪失から独立していない |
| 課題内履歴 | D1のカード | 締切・提出・訂正の過去 | 編集操作の証跡。学校の成績証明ではない |
| 保存版 | D1 revisions、現在は自動削除なし | 保存時点の学期を追加方式で回復 | 容量は増える。永続無制限の保証はしない |
| Time Travel | Cloudflare内、Freeは7日 | DB全体を以前の状態へ | 別ユーザーの直近変更も巻き戻す。独立保管ではない |
| JSON／SQLエクスポート | 利用者／運営者が別保管 | アカウント・サービス障害や古い状態 | 最後のバックアップ以降の変更は含まれない |

## 利用者の復元

### 誤削除

画面下のTrash → 対象カードのRestore card。過去の提出と締切を含めて戻る。誤って完了にした場合はSubmittedのUndo completion。完全削除・ごみ箱の自動消去は行わない。

### 別バックアップ

Export backup → JSONをダウンロードし、アプリやブラウザとは別の安全な保管先へコピー。JSONは平文なので共有リンクで公開しない。推奨は重要な更新後と移行前。運営者の日次SQLバックアップと併用する。

Backup & recovery → Choose JSON backup → 追加／同一内容／復旧コピーの件数を確認 → Import。科目・カード・ごみ箱・課題内履歴を含む。今の学期を丸ごと置き換えない。違う内容の同じIDはRecovered copyとして追加するので、両方を見て不要な方をごみ箱へ移す。取り込みを繰り返しても同じ復旧コピーを増やさない。

元のカードがごみ箱に残っている場合は、まずTrashから戻すと重複を避けられる。保存版の復元も同じ追加方式。履歴一覧は30版ずつOlder versionsで読める。確認中に別端末が保存した場合は、古いプレビューを適用せず再レビューする。

### 通信切断・競合

Savingは送信中、Savedはサーバー応答確認済み。オフライン・未再送コピーがある場合はUnsynced、失敗はSave failed。1件の保存待ちがある間は次の確定保存を止める。失敗データを空一覧へ置き換えない。再接続またはRetry syncで同一操作IDを再送する。

再読み込み後は同じアカウントでログインし、Backup & recoveryのResume sync。異なるアカウントの未同期コピーは表示しない。別端末の更新がある場合はConflictとなり、Keep both versionsで差分を復旧コピーとして追加する。元の分岐も端末に保持する。

Download local recovery filesは下書き・未同期・競合元をそのまま束ねた救出用アーカイブで、通常の学期バックアップとは別形式。必要なら次で**新しい空フォルダ**へ展開する。

```sh
cd app
node --experimental-strip-types scripts/unpack-recovery.mjs /path/to/local-recovery.json /path/to/new-recovery-folder
```

`recovered-*.json` は通常のImportから復元できる。`draft-*.json` は課題名・期限の原稿を保持し、それを見てカードを再入力する。壊れた個々のコピーは処理を中断して原ファイルを残す。コピーを捨てる前に必要な内容を確認する。

### 旧ブラウザ保存の移行

同じブラウザ／同じホスト名／同じポートならReview old browser dataでv1キーを読む。内容を検証・レビューしてからログイン中のアカウントへ追加する。元キーの値を変更しない。別の保存領域なら旧版を元のアドレスで開き、Exportしてファイル経由で取り込む。旧ソースは再設計前アーカイブに保管済み。

不正JSON・存在しない日付・重複ID・最後の履歴と現状の不一致・400 KB等の上限超過は拒否する。大きなv1バックアップを黙って一部だけ移行しない。分割・上限見直しが必要なら原本を保管したまま対応する。

## 運営者の別バックアップ

まずローカルの演習：

```sh
cd app
node scripts/backup-d1.mjs --local wrangler.local.json .local-backups
```

実サービス接続後、読み取り専用のリモート書き出し：

```sh
node scripts/backup-d1.mjs --remote wrangler.production.json /absolute/private-backup-directory
```

各SQLにSHA-256・時刻・バイト数のmanifestを作る。失敗時は成功と報告しない。SQLとmanifestを**端末やCloudflareアカウントから独立した安全な保管先**へコピーする。スクリプトだけでは独立保管にも自動バックアップにもならない。

運用案：評価期間は日次、変更・移行前には追加取得。日次7本・週次4本を別保管し、月1回空の評価DBへ復元演習。担当者が日次実行・保管先を決めてから実学生データを入れる。日次の場合の目標RPOは最大24時間、RTOは演習計測で決める。今回、自動スケジュールやクラウドバックアップ保存先は設定していない。

## SQL復元

1. 書き込みを止める時刻と対象を決め、現在のDBも書き出す。
2. manifestのハッシュを照合する。
3. **新しい別DB**へSQLを取り込む。現在DBへそのまま実行しない。新しいDBのIDで独立したWrangler設定を用意する。
4. `workspaces` と `revisions` の所有者・revision・JSON・操作ID・時刻を照合し、履歴トリガーも確認する。テストアカウントで読取・保存・復元を試す。
5. 接続先切り替えは利用者への影響を確認してから実施し、元DBをロールバック用に保管する。

例（確認用DB、ローカル）：

```sh
npx wrangler d1 execute RESTORE --local --config .local-backups/restore-check.json --file /path/to/backup.sql
```

2026-09-11にWranglerの実SQL書き出し→新しいローカルD1への取り込み→再書き出しを実施。workspace 1行、revisions 3行と2つの履歴トリガーの一致を確認した。統合テストでも別DBへのコピー復元を検証する。

**Firebaseの認証アカウントはD1 SQLに含まれない。** D1の所有者uidと同じFirebaseプロジェクト／uidを維持する必要がある。Firebaseプロジェクト削除等からの復旧はこのバックアップだけでは完結しない。認証アカウントの管理エクスポート・復元は実サービス設定後の運用課題。利用者のJSONは、新アカウントへ本人が取り込む回復経路としても使える。

## D1 Time Travel

[公式手順](https://developers.cloudflare.com/d1/reference/time-travel/)に従い、復元前のbookmarkとSQLを必ず取得する。Freeは7日、Paidは30日。DB全体の状態が変わるため、特定カードの誤削除にはアプリのごみ箱／保存版を優先する。

`wrangler d1 time-travel info` でbookmarkを取得し、対象時刻を確認してから `time-travel restore --bookmark=…` を使う。復元操作は影響範囲を承認した後に行う。ローカルエミュレーターは実Time Travelの検証代替ではなく、今回の実クラウド演習は未実施。

DB全体を巻き戻した後、端末のrevisionが復元先より大きい場合がある。利用者へ再読み込みを案内し、未同期コピーはエクスポートしてからレビュー・追加方式で回復する。復元後のrevisionを旧端末が強制上書きする操作を設けない。
