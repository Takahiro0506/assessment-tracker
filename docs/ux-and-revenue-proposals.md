「確認したうえで選んで反映する」という依頼に基づく実装判断。下の原案すべてを採用したわけではない。UX効果や購入意思はまだ測定していない。

| 提案 | 判断 | 反映内容・理由 |

### 収益化の前提で訂正する点

- **ローカルアプリを販売できない、とは言えない。** クライアント内の制限を改変できることと、ソフトウェアの販売が可能かは別問題。ソフトウェアのライセンス販売という方式は存在する（[Gumroadのライセンスキー機能](https://gumroad.com/help/article/76-license-keys)）。このWeb試作で厳密な利用期限を強制するには別の設計が必要だが、それだけで候補Aや一回払いを否定しない。販売できることは、学生が購入する根拠にもならない。
- **ICS購読URLはコピー不能ではない。** URLも取得された予定も複製可能。推測困難なURLでも共有・漏えいは起こり得るため、採用時には失効・再発行・公開範囲・課金終了後の扱いを設計する。
- **ファイル書き出しと購読は異なる。** ファイル取り込みはその時点のコピー。購読は受信側が定期取得する一方向の更新で、即時同期ではない。受信側が更新タイミングを決めることは[MicrosoftのICS説明](https://support.microsoft.com/en-us/outlook/calendar-sharing-in-microsoft-365)にも明記されている。通知は受信側のアプリ・権限・設定の実機検証が必要で、今回「必ず通知が届く」と約束しない。
- **人数だけで無料運用を保証しない。** Cloudflareの枠はリクエスト、CPU、D1の読取・書込・保存量などで定まる。数百人でも利用頻度やクエリ設計で変わる（[Workers料金](https://developers.cloudflare.com/workers/platform/pricing/)、[D1料金](https://developers.cloudflare.com/d1/platform/pricing/)）。決済・サポートなども含めた利益を確認する。
- 学生の科目数、サブスクへの抵抗、価格A$7〜9への反応、ブログとの相性は未検証。「コーヒー1杯」「効果が最も大きい」などの表現は仮説・比喩であり、調査結果として扱わない。

以下は原案をベースにした提案記録。断定の訂正はこのレビューを優先し、採用済みの仕様はproduct-briefを参照する。

## 要約

現在の試作は、データ処理・履歴保持・破損保護の作りが堅い。一方で「初見の人が価値を感じるまでの導線」と「今週なにをやるかの把握」が弱い。収益化より先にこの2点を直すと、初見ユーザー評価の結果が読み取りやすくなる。

収益化は、localStorage 完結のままでは技術的に成立しない（後述）。サーバー側にしか置けない機能だけが有料にできる。

優先度の高い順に記す。

---

## A. UX改善の提案

### A-1. サンプルデータを空状態へ昇格（最優先）

**現状**：初回起動は空リストで、`Add your first assessment below.` のみ。架空データはページ末尾の `<details class="demo">` に隠れている。

**課題**：このアプリの価値は「複数件たまった一覧を一目で把握できること」にある。0件では価値が見えない。初見ユーザーは数件入力した時点で「で？」となり、離脱しやすい。今のまま初見評価を行うと「使いにくい」ではなく「価値が伝わらない」という結果が出て、原因を取り違えるおそれがある。

**提案**：

- 空状態の中央に `Try a sample week` を配置する（フッターの `<details>` から昇格）。既存の `demoData('normal')` をそのまま使える
- サンプル読込中は上部に「これはサンプルです / Clear and start fresh」のバーを出す
- 体験順を「見る → 納得 → 自分のを入れる」に変える。現状は「入れる → やっと見える」で逆

**根拠**：初見評価の前提条件。実装コストは小さく、効果が最も大きい。

---

### A-2. Needs work を時間で自動グルーピング

**現状**：work / waiting / done の3セクション。各セクションは締切順のフラットリスト（`byDue`）。締切未定のみ先頭に分離済み。

**課題**：集中時24件ではスクロールしないと全体像が掴めない。学生の問いは「締切順は？」ではなく「今週なにをやる？」である。

**提案**：Needs work の内部を、追加入力なしで自動分割する。

```
Overdue            (due < today)
Due today / tomorrow
This week          (今週末まで)
Next week
Later
No date yet        (既存の undated グループ)
```

`due` と `today` は既に state にあるため、**新しい入力項目は不要**。product-brief の「所要時間・進捗率・優先度の必須入力を含めない」方針と矛盾しない。

**根拠**：入力コストを1つも増やさずに把握速度を上げられる。検証で測る「何が未提出かの把握」に直接効く。

---

### A-3. overview の数字をフィルタにする

**現状**：`3 need work` `1 overdue` `2 without a date` は表示のみで、押しても何も起きない。

**提案**：クリックで該当グループへスクロール、または絞り込み表示に切り替える。押せそうな見た目なら押せるようにする（押せないなら見た目を弱める）。

---

### A-4. 入力をタイピングからタップへ

登録時間を検証指標にする以上、入力操作そのものを削る必要がある。

**Unit（科目）**

- 現状は `<datalist id="units">`。iOS Safari で挙動が安定しない既知の問題がある
- 提案：直近使用した科目を**チップ（ボタン）で3〜5個**表示し、タップで選択。1学期の科目は4〜6個に固定されるため、ほぼタイプ不要になる
- `datalist` は PC 用に残してよい

**Due date（締切）**

- 現状は `<input type="date">` のみ。ピッカーを開く操作が重い
- 提案：`Today / Tomorrow / Fri / +1 week / No date` のクイックチップを添える。任意の日付だけピッカーへ

**維持すべき点**：追加後に科目を引き継ぎ、課題名欄へフォーカスを戻す挙動は良い設計。変えない。

---

### A-5. ステータス操作を1タップに

**現状**：`Update status` → ダイアログ → `Mark completed` / `Needs resubmission` の2択。

**課題**：選択肢が2つのダイアログは1タップ分の無駄。ラベル `Update status` も何が起きるか伝わらない。

**提案**：

- 行内に `Completed` と `Resubmit` を並べる（または split button）
- 再提出は新しい期限の入力があるため、ダイアログを残してよい。完了だけ即時化するだけでも効果がある
- ラベル案：`Passed` / `Resubmit`、あるいは `Result?`

---

### A-6. 一覧の視覚的ノイズを減らす

- **History の `<details>` が全行に常設**されている。行を開いた時、または編集時にのみ表示する
- **カラムヘッダ（Unit / Assessment / Due date / Action）が3セクションで3回**繰り返される。1回で足りる
- Completed セクションは初期状態で閉じている（`open.done = false`）。これは正しい

---

## B. アーキテクチャの提案（有料化に進む場合の前提）

### B-1. `app/page.tsx` の分割

**現状**：805行の単一コンポーネントに、状態管理・localStorage I/O・行描画・4種類のダイアログが同居している。

**課題**：試作としては許容範囲だが、この上に認証・クラウド同期・課金を積むと保守できなくなる。

**提案**：

```
lib/storage.ts            StorageAdapter インターフェース
  localStorageAdapter     無料版
  cloudAdapter            有料版（後から追加）
hooks/useAssessments.ts   commit / blocked / unsafe のロジック
components/AssessmentRow.tsx
components/AddForm.tsx
components/StatusDialog.tsx
```

**要点は保存層をインターフェースの裏に隠すこと**。今やれば同期の追加は差し替えで済むが、後からだと書き直しになる。

**既に良い点**：`lib/assessments.ts` が純関数として分離され、テスト可能になっている。同じ思想を保存層へ広げるだけでよい。

## C. 収益化の提案

### C-1. 前提：機能制限だけでは課金は成立しない

localStorage で完結するアプリの機能制限は**すべてクライアント側にあり、開発者ツールで解除できる**。「試用期間後にロック」も同様で、防ぐにはライセンス検証サーバーが要る。

したがって **サーバー側にしか置けない機能だけが、有料にできる機能**である。これは好みではなく技術的制約。

product-brief の候補A（期間付き一回払いで全機能）は、この理由から単独では成立しない。候補B（クラウド保存・同期・カレンダー連携を有料化）の方向が技術的に妥当。

### C-2. 提案する線引き

| | 無料 | 有料 |
|---|---|---|
| 課題管理・履歴・再提出 | フル機能 | 同じ |
| ローカル保存・Export / Restore | あり | あり |
| クラウド保存・端末間同期 | なし | あり |
| カレンダー購読URL（ICS） | なし | あり |
| 自動バックアップ | なし | あり |

**無料側を件数制限で不便にしない**。件数制限は、ユーザーが最も価値を感じた瞬間に壁を出す設計で、評判を損ねる。無料をフル機能にしておけば良い評価が得られ、その中から「PCとスマホ両方で見たい」「消えるのが不安」という人だけが払う。

なお、データ消失の不安を煽って売る形にはしない。Export は無料のまま簡単に使えるようにしておく。

### C-3. 有料フックの第一候補：ICS購読URL

`https://.../feed/<token>.ics` を発行し、スマホの標準カレンダーに購読させる。

- サーバー側にしか存在しないため**コピーできない**
- 通知機能を自作せずに「締切がカレンダーに出る＝通知が届く」が実現する
- 実装コストは双方向同期より軽い
- product-brief の「ICS書き出し」案の自然な発展形。自動同期ではないことは引き続き明示する

「アプリを開かなくても締切が目に入る」という利点は、単なる同期より訴求が明確。

### C-4. インフラ

Cloudflare Pages + Workers + D1（いずれも無料枠）。数百ユーザー規模までは月額コストが実質ゼロ。Vercel Hobby の非商用制限を避ける方針とも整合する。公開前に、その時点の利用条件と費用を再確認する。

### C-5. 価格の考え方

学生向けにサブスクリプションは相性が悪い。コース期間が6ヶ月〜2年あり、月額を意識され続けることが離脱要因になる。

- **A$7〜9 / セメスターの買い切り**を提案する
- 「1学期ぶんのコーヒー1杯」で説明できる金額
- 更新を能動的にする（自動課金しない）ことで、返金・解約対応の負荷が下がる。個人開発ではこの運用コストが軽視できない

A$9.90 は仮案のまま。金額も課金方式も未確定。

## D. 流入経路の提案

UX も課金も、**使う人が来なければ結果はゼロ**になる。tasks.md の「対象学生に届く経路の確認」が未着手であり、ここが実際のボトルネック。

現状、構造的なズレがある：**アプリは英語UI（TAFE学生向け）／既存の集客資産（運営中のブログ tajanajaworld.com）の読者は日本語（留学系）**。この2つが繋がっていない。

**選択肢A（低コスト・先に試す）**：ブログ読者向けに日本語ランディングページを作る。アプリUIは英語のまま、説明だけ日本語。既存トラフィックで「そもそもリンクを踏んで使うか」を測れる。

**選択肢B（時間がかかる）**：英語圏のTAFE学生に届く経路を新規開拓する（Reddit、各TAFEの学生コミュニティなど）。

**まず A で反応を測る**ことを提案する。コストがほぼ無く、最も早く答えが出る。ここでも、少人数の反応から需要や購入意思を断定しない。

## E. 提案する順序

1. サンプルデータを空状態へ昇格（A-1）
2. 時間グルーピング＋overview のフィルタ化（A-2、A-3）
3. 科目チップ・日付クイックチップ（A-4）
4. ステータス操作の1タップ化・History の整理（A-5、A-6）
5. **初見ユーザー評価を実施**（verification.md の手順）
6. 評価が良ければ保存層のリファクタ（B-1）→ 無料フル機能のみで公開
7. 日本語ランディングページを出し、流入を測る（D）
8. 実際に継続利用者が出てから、ICS購読・同期を有料機能として作る（C）

**6・7が先で、有料機能は最後**。課金の仕組みを作ってから誰も来なかった、という形が最ももったいない。
